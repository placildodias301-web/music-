## Major Features

### Music Analysis

Every uploaded song or YouTube URL goes through a 10-step analysis pipeline:

1. Audio load and normalisation (librosa)
2. BPM detection (`librosa.beat.beat_track`)
3. Key signature detection (chroma + template matching)
4. Scale detection (chroma → pitch class scoring)
5. Energy measurement (`librosa.feature.rms`)
6. Chord detection (basic-pitch → note events → template matching)
7. Difficulty scoring (heuristic: BPM factor × chord complexity × chord variety × change rate)
8. MIDI export (music21)
9. Sheet music PDF (music21 + LilyPond)
10. Stem separation (Demucs `htdemucs` — vocals, drums, bass, other)

Steps 7–10 are plan-gated; results are uploaded to Cloudflare R2.

### AI Tutor

Conversational music theory assistant available to PRO, STUDIO, and ENTERPRISE users. The tutor is aware of the song being discussed: it receives key, BPM, scale, and chord list as context. Primary model: `claude-haiku-4-5-20251001`. OpenAI `gpt-4o-mini` is the fallback. A mock fallback is used if neither key is set (development mode).

Monthly limits: PRO = 500 messages, STUDIO = 2,000 messages, ENTERPRISE = unlimited.

### Billing and Subscriptions

| Provider | Platform | Method |
|---|---|---|
| Stripe | Web | Checkout Session + webhook (`customer.subscription.*`, `invoice.payment_failed`) |
| Razorpay | Web (India) | Order + HMAC verify + webhook (`payment.captured`) |
| Apple IAP | iOS | Receipt verification via Apple `/verifyReceipt` |
| Google Play | Android | Purchase token via Google Play Developer API |

All webhook handlers have Redis NX idempotency (24h TTL) to prevent double-processing on replays.

### Community

Users can publish their song analysis to the community feed with optional commentary. Posts can be liked. Feed is public (read-only for FREE users, write-enabled for all verified accounts).

### Administration

ADMIN-role users have access to:
- User list with plan filter, search, and account management
- Platform analytics: registered users, daily active users, total analyses, revenue estimate by provider
- Queue health: BullMQ analysis queue depth, failed jobs, processing status

## Architecture

Four independently deployable services:

| Service | Stack | Runtime |
|---|---|---|
| Backend API | Fastify 5, Node.js 22, TypeScript, Prisma 6, BullMQ 5 | Railway |
| AI Service | FastAPI, Python 3.12, Celery, librosa, Demucs, basic-pitch | Railway |
| Web Dashboard | Next.js 14 App Router, Tailwind CSS, Zustand 5, TanStack Query v5 | Vercel |
| Mobile App | Expo SDK 54, React Native 0.76, expo-router 6 | EAS (App Store + Play Store) |

Supporting infrastructure: PostgreSQL 16 (Railway), Redis 7 with AOF persistence (Railway), Cloudflare R2 (object storage), Resend (transactional email), GitHub Actions (CI/CD).

All inter-service communication uses HTTP with `X-Internal-Secret` header authentication. Backend→AI service calls are fire-and-forget via BullMQ; AI service callbacks are HTTP POSTs back to the backend.

### Security Model

- JWT 15-minute access tokens + 30-day httpOnly refresh cookies; refresh rotated on every use
- Email verification required before uploads and tutor access
- `AI_SERVICE_SECRET` — startup `process.exit(1)` if unset in production (both backend and AI service)
- Webhook HMAC verification with `timingSafeEqual` (Stripe and Razorpay)
- Webhook idempotency via Redis NX (24h TTL, all four providers)
- Rate limiting on all auth endpoints; `@fastify/rate-limit` global + per-route
- Magic-byte file validation on upload (MP3/WAV/FLAC/M4A/OGG/AIFF/WebM)
- BullMQ job entitlements resolved at enqueue time from user's plan (prevents privilege escalation via re-enqueue)

## AI Features

### Analysis Pipeline

The full pipeline runs in the AI service via Celery workers on two queues:
- `fast_queue` — BPM, key, scale, energy, chords (~10s)
- `slow_queue` — stems, sheet music (~120s)

Retries use exponential backoff. Failed jobs are forwarded to a dead-letter queue for alerting.

### Real-Time Chord Detection

PCM audio frames streamed from the client microphone via Socket.IO `live:audio-chunk` event. The AI service `/api/realtime/chunk` endpoint performs autocorrelation pitch estimation and returns chord + confidence + timestamp.

## Known Limitations

### Analysis Difficulty Display

The AI service computes a `DifficultyResult` (score, label, BPM factor, chord complexity, chord variety, change rate). The worker receives this but the `Analysis` Prisma model has no `difficulty` column. The result is dropped; the difficulty section on the web-app analysis page is conditionally rendered and remains hidden. **Fix planned for v1.1:** add `difficulty Json?` to the Analysis model, write the field in the worker, return it from `AnalysisService.get()`.

### Analysis Mode Display

The AI service returns the key mode (`"major"` / `"minor"`). The worker receives it but the `Analysis` Prisma model has no `mode` column. The result is dropped; the key display on the analysis page shows key signature only (e.g. `"C"` instead of `"C major"`). **Fix planned for v1.1:** add `mode String?` to the Analysis model, write the field in the worker.

### No Automated E2E Tests

The full upload → analysis → tutor → billing flow is tested manually only. Playwright E2E suite is planned for v1.1.

### No Mobile CI Pipeline

The mobile app has no automated CI. TypeScript errors are caught locally; the app is tested manually on iOS simulator, Android emulator, and real devices. EAS CI planned for v1.1.

### AI Service Test Environment

98 of 100 AI service tests pass in the full Python venv with all ML dependencies. 2 tests are skipped (GPU-dependent Demucs model download). In a bare Python environment without the venv, tests cannot run due to missing ML dependencies (`soundfile`, `librosa`, etc.).

## Upgrade Notes

v1.0.0 is the initial public release. There is no upgrade path from a prior stable version. Existing internal builds (`v0.x.x`) should be replaced in their entirety.

Database: Run `prisma migrate deploy` before starting the server. The Dockerfile CMD already does this automatically: `prisma migrate deploy && node dist/index.js`.

Environment variables: See [docs/ENVIRONMENT.md](../deployment/ENVIRONMENT.md) for the full reference. Required variables: `DATABASE_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET`. Production also requires `AI_SERVICE_SECRET` (startup FATAL if unset).
